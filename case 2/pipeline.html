Case 2: Reality Gap Pipeline

Robotics Summer School 2026 — Bridging the sim-to-real gap with distillation + RL

1 — The Problem: Reality Gap

URSim (Simulator)

The simulator tracks commanded currents perfectly. Gap ≈ 0 A — not representative of hardware.

Real UR10e

Real hardware has lag, inertia, friction, ringing. actual_current ≠ target_current — this difference is the reality gap.

What we do: Train a LinearModel on real recordings to predict the gap from commanded values (distillation). Then use RL to find motion parameters that minimise the predicted gap without needing the real robot at every step.

3 — Script Details

① record.py

Passive RTDE stream logger. Never moves the robot. A script must already be playing. Records target/actual joint positions, velocities, currents, and any float registers you map (e.g. vel, acc) to a CSV.

Inputs
--robot-ip controller address
--float-register 1 vel 2 acc register-to-name map
Output
data/test-N.csv raw RTDE recording
python record.py \
  --robot-ip 127.0.0.1 \
  --out data/test-1.csv \
  --float-register 1 vel 2 acc
② train_distillation_model.py

Trains a LinearModel via least-squares on features [target_current, qd, qdd, pos, vel, acc, joint_onehot] → actual_current. Evaluates on a held-out split, then refits on all data.

Inputs
data/test-*.csv real robot recordings
Outputs
models/distill.pkl latest
results/<dt>/distill.pkl versioned
results/<dt>/log.json — features, RMSE, R²
results/<dt>/residuals.png + per_joint_rmse.png
results/runs_summary.csv — cross-run comparison
python train_distillation_model.py \
  --csvs data/test-4.csv data/test-5.csv \
  --out models/distill.pkl
③ train_rla.py

Runs training scripts on URSim, augments actual_current with the distill model, then trains a PPO contextual bandit to minimise current gap + cycle time. Triangle is held out as the test script.

Inputs
models/distill.pkl
scripts/*.script (training motions — not triangle)
Outputs
models/agent_params.zip latest
results/<dt>_rla_params/agent_params.zip versioned
results/<dt>_rla_params/sim_to_real.csv
results/<dt>_rla_params/training_curve.png
python train_rla.py \
  --mode params \
  --model models/distill.pkl \
  --robot-ip 127.0.0.1 \
  --scripts scripts/shoulder_swing.script \
            scripts/vertical_swing.script \
  --loop 5 --steps 20000
④ run.py

Runs the held-out script on URSim, loads the trained agent, queries it for better motion parameters, scores the predicted improvement, and writes the optimised script or path file.

Inputs
scripts/triangle.script
models/distill.pkl + models/agent_params.zip
Outputs
scripts/triangle.optimized.script (params mode)
scripts/triangle.path (path mode)
results/<dt>_run_params/log.json — baseline vs optimised
python run.py \
  --mode params \
  --script scripts/triangle.script \
  --model models/distill.pkl \
  --robot-ip 127.0.0.1
⑤ send.py

Sends a URScript (or servoj path) to the robot and records RTDE at 125 Hz. Output is auto-named with datetime when --out is omitted — nothing is ever silently overwritten. A JSON sidecar is always saved next to the CSV.

Inputs
scripts/triangle.script or .optimized.script
Outputs
results/<dt>_triangle.csv
results/<dt>_triangle.csv.json — script, loop, n_samples
# baseline recording
python send.py \
  --script scripts/triangle.script \
  --loop 10

# optimised recording
python send.py \
  --script scripts/triangle.optimized.script \
  --loop 10
⑥ analysis.py

Reads any recording CSV. Prints a per-joint table (range of motion, current gap RMS/max, position error) and saves two plots. Use on both baseline and optimised recordings to validate improvement.

Inputs
results/<dt>_triangle.csv any recording
Outputs
results/<dt>_analysis_<name>/log.json
results/.../current_shoulder.png — target vs actual
results/.../all_joints_overview.png — 3-panel bar chart
python analysis.py \
  --csv results/<dt>_triangle.csv \
  --joint 1  # 0=base 1=shoulder … 5=wrist3

4 — The Two Modes

params mode (GapEnv)

Agent picks a single global vel and acc for all moves. The existing script is rewritten with new values → .optimized.script. Simpler, recommended to start.

path mode (PathEnv)

Agent picks a speed profile shape (accel_frac, decel_frac, dt per move). Output is a dense servoj setpoint file → .path. More flexible but needs send.py --path.

5 — RL Environment: Contextual Bandit

A key design decision: every episode is a single move and terminated=True always. This means the PPO agent never needs to reason about multi-step consequences — it's essentially a learned lookup from move features → optimal parameters. This is called a contextual bandit.

9 — CSV File Schemas

Recording CSV  — produced by record.py and send.py

Every row is one RTDE sample (default 125 Hz, so ~8 ms between rows). Each joint has its own numbered column, 0 = base through 5 = wrist3.

Column(s)UnitWhat it is
timestampsSeconds elapsed since the recording started
target_q0 … target_q5radJoint positions the controller is commanding (the setpoint)
actual_q0 … actual_q5radJoint positions the encoder actually reads. On URSim this equals target_q.
target_qd0 … target_qd5rad/sCommanded joint velocities
target_current0 … target_current5ACurrent the controller asks the motor driver to produce (from its internal model)
actual_current0 … actual_current5ACurrent the motor driver reports drawing. On real hardware this differs from target — that difference is the reality gap. On URSim it equals target_current.
velrawThe vel argument passed to movej(…, a, v, …) in the script, logged via float register 1. Raw URScript units (~100 = moderate speed).
accrawThe acc argument passed to movej, logged via float register 2.
script_line_counterintWhich URScript line is executing. Changes at every waypoint. Used by common.segments() to split the recording into individual moves.

tip: Load with from analysis import Recording; rec = Recording("results/…csv"). Use rec.target_current, rec.actual_current (both shape (n, 6)) and rec.current_gap(joint) = actual − target for one joint.
sim_to_real.csv  — produced by train_rla.py and run.py

Same schema as the recording CSV, but actual_current0–5 has been overwritten by the distillation model's predictions. This is what makes RL training possible without a real robot: the simulator runs the motion, and the distill model fills in what the real currents would have been.

10 — How to Interpret and Compare Results

Distillation model quality
RMSE (held-out)
< 0.3 A — excellent 0.3 – 0.8 A — usable > 1.5 A — too noisy, collect more data
R² (held-out)
> 0.90 — excellent 0.70 – 0.90 — acceptable < 0.50 — weak, need more or better data
residuals_*.png
Errors should be centered around 0 and roughly bell-shaped. A skewed distribution means systematic bias — the model consistently over- or under-predicts.

per_joint_rmse_*.png — shoulder (1) and elbow (2) typically have higher RMSE because they carry more load and experience greater gravity-induced current swings. Wrist joints (3–5) are usually easier to predict. If one joint is dramatically worse, check that you have recordings with that joint moving significantly.

Improving the model: add more training CSVs (more variety of motions), check that vel / acc registers were logged (they are important features), and try different scripts to cover a wider range of joint configurations.

runs_summary.csv comparison: sort by rmse_actual_current ascending. Adding recordings should monotonically improve RMSE; if a new run is worse, the new CSV might have recording artefacts (robot not warmed up, e-stop during recording, etc.).

RL agent quality

training_curve.png has three panels — read them together:

PanelWhat to look for
Score over timesteps Should trend downward. A flat line means the agent isn't learning (try more steps or check the distill model quality). A U-shape (goes down then up) means it diverged — use the versioned model saved at the best point, not models/agent_params.zip.
Cycle time over timesteps Should decrease or stabilise. If it keeps decreasing while score stays flat, the agent is optimising for speed only — the λ weight in the reward may need adjusting.
Reward over timesteps Should trend upward (reward = −score). Rolling mean smooths noise. If reward never rises, the reward signal is too weak to learn from.

runs_summary_rla.csv comparison: sort by best_score ascending. Compare runs with different step counts or training scripts. A large gap between best_score and final_score tells you training was unstable — prefer the versioned checkpoint.

Key limitation: the agent learns from predicted gaps (distill model on URSim), not real hardware. If the distill model is poor, the agent will optimise for phantom improvements. This is why model quality comes first.

Comparing baseline vs optimised recordings

After running send.py for both scripts and analysis.py on each, compare the all_joints_overview.png bar charts side by side, or compare log.json values directly.

MetricBaseline vs OptimisedIf optimised is worse
gap_rms_A Should decrease. This is the primary success criterion — the robot's actual current is closer to commanded. The distill model may not generalise to the triangle script. Try training on more scripts or improving model RMSE first.
gap_max_A Should decrease, especially at waypoints (start/stop of moves). High max with low RMS = occasional transients. Ringing during deceleration is common at high acc values.
pos_err_mrad Should decrease or stay similar. Path mode typically improves this more than params mode. An increase means the optimised parameters cause the controller to miss the target more. Consider reducing acc.
Cycle time The optimised script may run faster (fewer seconds per loop). Compare total recording duration / loop count. A much faster script with worse gap = agent over-optimised for speed. Expected if λ is too high.

Cross-checking with run.py predictions: run.py prints improvement.score_pct — the predicted improvement. After running on hardware, compare this to the actual change in gap_rms_A from analysis.py. If they match, the distill model generalises well. If the real improvement is much smaller (or negative), there is a sim-to-real gap in the distill model itself.

On URSim: gap_rms_A will always read 0 because the simulator is perfect. To get predicted (non-zero) gap values from a URSim recording, call augment(model, "results/…csv") first — this overwrites actual_current columns with the distill model's predictions. Only then will analysis show meaningful numbers.
